# Multiplayer protocol (version 2)

This is the protocol used by every phase of the game: lobby, briefing, design, constraints, verification, mission and debrief. The code is in `src/red/`. (Message names, field names and identifiers are kept as they appear in the code, in Spanish.)

## 1. Overview

- **One host with authority.** One of the players is the host. The others send it **intents** ("I want the science role"). The host validates them, applies them to the state and sends everyone the **full state**.
- **Nobody else changes the state.** So there are no conflicts: if two players ask for the same role at once, the host decides and the other one receives a notice.
- **Randomness is decided by the host.** It draws the events and writes the result into the state. Everyone sees the same thing without having to synchronize random generators.
- **Ephemeral data goes separately.** Where each head is looking, the scenario each player votes for at the projector (`voto`) and, later, cursors or the part being dragged, are **presence**: each player broadcasts it to the others without going through the host, and it is neither retried nor stored.

The state weighs a few KB and changes at the speed of clicks, so sending it whole every time is simpler and more robust than sending diffs.

## 2. Messages

All carry `v` (protocol version).

| Type | From → to | Content | Purpose |
|---|---|---|---|
| `hola` | anyone → anyone | `jugadorId`, `nick`, `etiqueta`, `r?` | Introduce yourself. The initial greeting is **always** answered; the reply carries `r: 1` and is not answered in turn (avoids ping-pong). Repeated until synchronized |
| `estado` | host → everyone (broadcast) or → one player | `etiqueta {term, host, seq}`, `estado` | Full state after every change (broadcast), and directed when answering a `hola` from someone who is behind |
| `intent` | player → host | `jugadorId`, `intencion {id, tipo, payload}` | Ask for a change |
| `aviso` | host → one player | `id`, `motivo` | Rejection of an intent, with the reason to display |
| `pres` | player → everyone (broadcast) | `datos` | Ephemeral presence (gaze) |
| `chat` | player → everyone (broadcast) | `texto` (≤ 200), `nick` | Room chat. Ephemeral, outside the state and the rules; the sender paints its own message (no echo) |

## 3. Identity

- **`jugadorId`** is stored in `sessionStorage`: it survives reloading the tab, but two tabs are two players.
- The peer id (`peerId`, the `selfId` generated by the transport) changes on every load, so it is only used for routing. Roles are tied to the `jugadorId`.
- The host checks that the `jugadorId` of an intent matches that of the connection sending it: nobody acts on behalf of another.

## 4. Who is the host

**Tag** (`etiqueta`) = `{term, host, seq, peso}`. `peso` = `[phase, players who have passed through the room]`. A state replaces another if its tag wins:

1. the highest `term`;
2. with the same `term` and a different host, the higher `peso`: **a room with history never loses against a newcomer with an empty state**;
3. with the same weight, the `host` with the lower id;
4. with the same host, the highest `seq`.

**Startup.** On entering, the player greets and waits 5 s. If nobody sends it a state, it names itself host (`term` 1).

**Two hosts.** This is normal when two people open the link at the same time, because discovering each other takes a few seconds. It also happens when someone arrives late to a game in progress and finds nobody within 5 s. When they find each other, the one with the losing tag yields, adopts the winner's state and rejoins carrying its role and its role data. If the role clashes, the winner's stays and the other player receives a notice. By the weight rule, the late arrival always yields to the game in progress.

**Handover.** If the host disconnects, it is replaced by the connected player who has been in the room the longest (the lowest `orden`), with `term + 1`. If that successor does not show up within 6 s, it is discarded and the next one is used. Everyone has a copy of the last state they saw. What the host applied but did not manage to distribute before dropping is recovered because players resend their pending intents to the new host.

**The host reloads the page.** Its new connection may greet before the old one is noticed as closed. If a `hola` from the host arrives from another connection, its old session is considered dead and there is a handover without it. This way it does not come back as host with a blank state: it comes back as a player and recovers its role.

**Resynchronization.** A relay can lose an `estado` without telling anyone. While not synchronized, the player repeats its `hola` every 2 s. Once synchronized, every 3 retries (≈6 s) it shows its tag to the host with a reply `hola` (`r: 1`, so it is not greeted back). The host only resends the state if the tag is behind. This way a lost state is recovered by itself, without noise in an up-to-date room.

**Nothing depends on the render loop.** The browser throttles timers in background tabs. That is why the host's logic reacts to messages, and the transport keeps its clock in a Worker (see §9). A host dropping is detected by the transport (farewell, Last Will or heartbeats that stop coming back) and the session only reacts to the `alSalir` it receives. If it is the player themselves who loses the network, the transport does not mark anyone as gone (§9), so no host is named and `term` does not go up.

## 5. Intents

- **Increasing ids** (`max(Date.now(), last + 1)`). The host keeps `ultimaIntencion` per player and discards repeated ones: resending is safe.
- The player **keeps its pending intents** until it sees in the state that they were applied (or until it receives a notice). It resends them every 2 s and also to the new host after a handover.
- `unirse` is idempotent: it serves to enter, to come back after reloading and to rejoin after a handover or a merge.

## 6. State

```text
fase             lobby | briefing | diseno | restricciones | verificacion | mision | informe
jugadores        jugadorId → { nick, rol, orden, conectado, desconectadoEn, ultimaIntencion }
semilla          drawn by the host when the mission starts; design and flight events come from it
briefing         { objetivos, tareas, riesgos, carpetas }
mision           null | { escenario, id, dificultad: 'facil'|'normal'|'dificil', objetivos: [ids], plazo }
                 plazo = launch month committed to investors (months since reloj.inicio), from m.reloj.plazos; null without a clock
porRol           vuelo    { piezas, cohete, ruta }
                 ciencia  { piezas }
                 potencia { piezas }
                 comms    { piezas, contingencias: [id] }      (maximum 3)
                 piezas = { [piezaId]: { op, uso } }           (uso null if the part has no usage decision)
                 + free notes from editarPropio (any other key)
diseno           { revisiones, eventos: [{ id }], ultima }     design events already drawn; ultima =
                 { tipo: 'evento', id } | { tipo: 'revision', nivel, barras } (result of the last review)
firmas           { vuelo, ciencia, potencia, comms }           booleans
resultado        null | what simular() returned at launch
vista            { paso, activadas }                           flight steps already revealed, contingencies activated
ruta             { mes, sitio }                                planning in the control room: launch month (months since
                 reloj.inicio, null if not chosen) and site/orbit. `ventana` = copy of `mes` for the old interface (removed
                 in batch 2). v3 stored a day there: without `mes`, it is emptied when the state is completed
reloj            { mes, msPorMes, inicioMes, corriendo }       months elapsed since m.reloj.inicio (contrato-reloj.md). v5: runs in real time. inicioMes = host's Date.now() when the month began; corriendo only in design, constraints and verification; msPorMes = 60/75/90/105 s for 4/3/2/1 players with a role (motor.msPorMes)
registro         events already resolved by the host (future phases)
desistir         { votos: { jugadorId: true }, fase, firma }                   vote to abandon the mission (v6). `fase` and `firma` (ids of connected players with a role) are used to clear the votes if the phase or the group changes; in the interface only connected players with a role count
desistida        null | { id, escenario, mes }                                 last abandoned mission; the briefing shows it until another is chosen (also recorded in `registro` as { tipo: 'desistir', mision, mes, fase })
```

- **Derived values are not stored.** The bars, science, risks and the effects of design events are computed on each client with `resumen(estado, DATOS)` (`src/reglas/motor.js`). The state only holds ids, option and usage. The exception is `resultado`: the host computes it once, at launch, and it is the same for everyone.
- **Mission clock (v4, contrato-reloj.md).** Time only advances on validated host actions (v5): `tic` +1 month in real time (plus the `efecto.meses` of any design event that comes out), redesign (debrief → design) +6, new mission → 0. Everything that depends on the clock is derived in `resumen()`: `res.reloj = { activo, mes, plazo, lanzamiento, retraso, recorte, bono, cancelada, presupuesto }` and `res.plan = { mes, mesAbs, perdida, factor, extraKg, dv, horasEnlace, cond, cometa, … }` (`dia` = `mes` and `optimo: false` only for compatibility). Budget = mission · (1 + deadline bonus) · (1 − delay cut); then events: sums first, factors after. With a delay > 12 months the investors pull out: if this happens when the clock advances, the host stores a cancelled `resultado` (`cancelada: true`, verdict `fallida`) and moves to debrief. The new draws (`derivar(semilla, 'clima'|'reloj', misión, mesAbs)`) do not consume the existing ones.
- **Flight explanation.** `resultado.fallos = [{ codigo, fase, p, tirada, desglose: [[fuente, ref, dp]], decision, evitar }]`, `resultado.lanzamiento`, `resultado.reloj`: compact codes that `explicarCausas(resultado, DATOS, idioma)` (`src/reglas/explicar.js`) turns into "Cause → Decision → What would have avoided it". `resultado.causas` keeps its `{ en, es }` texts.
- **Data.** `protocolo.js` loads `src/datos/index.js` with a guarded `import()`: if it is missing or fails, the protocol still loads and game actions are rejected with "Game data not loaded". `usarDatos(d)` or `ctx.datos` inject other data (the tests do this).
- **Merge.** `unirse` only copies the workshop a player brings if the host's is empty (`tallerVacio`), and normalizes it (`normalizarTaller`).
- **Each role's "private" information.** The whole state is replicated to everyone: private data is only hidden in the interface. In a cooperative game that is enough, but it is not real secrecy.
- **Disconnections.** The role of a player who disconnects stays reserved for 20 s in the lobby and 90 s in the game, so that a reload does not lose it.

## 7. Actions (src/red/protocolo.js)

| Action | Phases | Rule |
|---|---|---|
| `unirse` | all | Maximum 4 connected. Recovers the role and role data if they do not clash |
| `elegirRol` | all | The role must be free or with an expired reservation. `null` releases it. Someone arriving to a game in progress takes a vacant role; when a role changes hands, its sign-off is cleared |
| `iniciarMision` | lobby | All connected players have a role. Draws `semilla` |
| `marcarPizarra`, `abrirCarpeta` | briefing | — |
| `editarPropio` | briefing, design, constraints | Free notes in your role's workshop. Maximum 8 KB per item and 32 KB per workshop. It cannot use the keys `piezas`, `cohete`, `ruta`, `contingencias` |
| `elegirMision` `{escenario?, id?, dificultad?}` | briefing | Validates against the data. Changing `id` empties piezas, cohete, ruta, contingencias, design events, firmas, resultado, `ruta` and `reloj` (notes are kept), and sets `plazo` = the middle one of `m.reloj.plazos` |
| `comprometerPlazo` `{plazo}` | briefing | `plazo` must be in `m.reloj.plazos`. First = short (+10 % budget), last = long (−10 %). Cancels the "ready" flags |
| `montar` `{rol?, pieza, op?, uso?}`, `quitar` `{rol?, pieza}` | design, constraints | The part belongs to the role and to the mission; `op` and `uso` within the sheet. Another `rol` only if vacant (nobody connected has it, MEC-03). In constraints, MEC-12. Clears the sign-offs |
| `elegirCohete` `{id}`, `elegirRuta` `{id}` | design, constraints | Flight role (or vacant). From the mission's list; rocket with `cumpleDEC09`. `null` removes it. Clears the sign-offs |
| `contingencia` `{id, on}` | design, constraints | Comms role (or vacant). Maximum 3. Clears the sign-offs |
| `tic` `{mes}` | design, constraints, verification | Host only (`ctx.reloj`); a client gets "Only the host clock can do that". `mes` must equal `reloj.mes` (avoids double ticks). Adds 1 month; if the investors pull out, mission cancelled and debrief. Then draws a design event with `derivar(semilla, 'evento', misión, mes)` (`motor.sortearEventoDiseno`): the mission's events spread up to the deadline according to difficulty (1/2/3) plus generic ones (`generico: true`, ≈7 % per month, max. 3). If one comes out: `diseno.ultima = { tipo: 'evento', id, mes }`, sign-offs cleared and, if it has `meses`, the clock jumps |
| `pedirRevision` `{revision?}` | design, constraints | No longer adds months or draws events. Overrun (> +20 %) → stays in design; within limit or tolerance (≤ +20 %) → verification (tolerance does not force cutting: it raises the failure probability of a phase, `motor.riesgoTolerancia`). `revision` (optional) = expected `diseno.revisiones`, avoids double clicks (MEC-10, MEC-11) |
| `firmar` `{rol?, on}` | verification | Your role, or a vacant one. To sign, `verificar()` must pass |
| `lanzar` | verification | Checks and 4 sign-offs. The host computes `resultado = simular()` and moves to mission |
| `avanzar` `{paso?}` | mission | `vista.paso + 1`; with all steps in view, moves to debrief. `paso` (optional) avoids double clicks |
| `planificarRuta` `{mes?, sitio?}` | design, constraints, verification | `mes` is set by flight (or vacant), `sitio` by flight or science. `ventana` is accepted as the old name of `mes`. Whole month in 0..mesMax; not before `reloj.mes` ("Launch month already passed"); in design and constraints, at least `reloj.mes + 1`; at most 12 months after the deadline. In constraints and verification it cannot raise a bar that ends up outside its limit, except to redo a lost plan. Clears the sign-offs |
| `votarDesistir` `{on: bool}` | design, constraints, verification, mission | Vote to abandon the mission (requires a role; `on` boolean). Votes are cleared when the phase changes, when a player with a role joins or leaves (or disconnects) and when the vote is withdrawn (`on: false`). When all connected players with a role vote yes: returns to the **briefing** with no mission (scenario and free notes are kept), empties design, firmas, resultado, ruta and reloj as when changing mission, and records `desistida` and `registro` |
| `cambiarFase` | all | Only the transitions in `TRANSICIONES`, except those with their own action (`SOLO_POR_ACCION`: review, launch, advance). briefing → design requires a `jugable` mission. debrief → design (redesign) keeps design, seed and design events; clears sign-offs and result; the clock advances 6 months (rejected with "Investors pulled out" if that would cancel the mission). → lobby empties the game |

The rejection reasons of these actions are in English: the interface shows them as they are.

**To add an action** in a new phase, add an entry to `ACCIONES` with `fases`, `validar` and `aplicar`. The network does not change.

## 8. Versions

If a `hola` arrives with a different `v`, a notice is shown ("reload the page") and its messages are ignored. A connected peer that has not greeted within 8 s is treated the same way: it is a version prior to this protocol. **When a change breaks compatibility, `VERSION_PROTOCOLO` must be bumped.** Current version: 6 (vote to abandon: `desistir`, `desistida`, action `votarDesistir`; before, v5: real-time clock: `reloj = { mes, msPorMes, inicioMes, corriendo }`, action `tic`; before, v4: `reloj`, `mision.plazo`, `ruta.mes`, `comprometerPlazo`). An old `reloj` with only `{ mes }` is completed without losing the month. `completarEstado` completes a v3 state: `ruta.ventana` → `ruta.mes = null`, `reloj = { mes: 0 }`, `mision.plazo = null` (no investor rule).

The host discards malformed intents (without a numeric `id`, without `tipo`, or with a `payload` that is not an object).

## 9. Transport (src/red/transporte-mqtt.js)

The session knows nothing about the network. It receives a transport with this interface: `selfId`, `enviar(tipo, datos, peerId?)`, `alRecibir`, `alEntrar`, `alSalir`, `pares()`, `enLinea()` and `salir()`. Without `peerId`, `enviar` broadcasts to the whole room. `transporte-memoria.js` is the simulated version for protocol tests.

The real transport is a **relay over MQTT on secure WebSocket**. There is no WebRTC: each browser opens outgoing TLS sockets to public brokers, and that goes through any NAT (but not through a network that filters the brokers' ports, see §11). The brokers (`RED.BROKERS` in `src/config.js`) are used **all at once and redundantly**.

**Topics** (`<appId>/sala/<CODIGO>/…`):

- `todos`: broadcast (announcements, heartbeats, farewells, state and presence).
- `a/<peerId>`: messages addressed to one peer, so that a directed state is not downloaded by the whole room.

**Envelope** (JSON): `{ d: sender, n: sender's message number, t: type, m: data, q?: 1 }`. The types `+` (announcement or heartbeat) and `-` (farewell) belong to the transport. `hola`, `estado`, `intent`, `aviso` and `pres` belong to the session and are delivered to it as they are. `q: 1` means "answer me".

**Redundancy and deduplication.** A reliable message is published with QoS 1 to all connected brokers and with the same `n`. The receiver keeps the first one that arrives and discards the others by `(sender, n)`. If a broker goes down or loses messages, the others cover for it. There is no guaranteed order between brokers; the session does not need it because the state is repeated whole and compared by tag.

**Discovery.** As soon as a broker confirms the subscription, the peer publishes an announcement with `q: 1`; whoever hears it answers and registers it, and `alEntrar` fires on both sides. After that each peer publishes a heartbeat (`+`) every 4 s.

**When a peer leaves: heartbeats counted in my own echoes.** Each heartbeat of mine comes back to me through the broker, because the subscription includes the sender. That echo proves my link works and marks a full round trip through the network. A peer I hear nothing from during 4 of my echoes (≈16 s) is considered gone. The wait is not measured in clock seconds, but in echoes.

**Farewell and Last Will.**

- A voluntary close (`salir()`, or `pagehide` when closing the tab) publishes a `-` farewell with its `n`. The others remove it instantly. That `n` is remembered: an earlier message arriving late through a slow broker is ignored and does not resurrect the peer.
- Each connection declares a **Last Will** (`{ d, t: '-', w: 1 }`). If the broker loses the socket without a DISCONNECT (10 s keepalive, detected in ≈15 s), it publishes it. It is lost by **one** broker, not necessarily the peer, so it does not expel it: the peer is asked through the other brokers and, if it does not answer within 2 echoes (≈8 s), it is considered gone. The clean close of `end(false)` does not trigger the Last Will.

**Critical rule: "I am offline".** If it is me who loses the network, I will see no echo and nobody expires: I do not emit anyone's `alSalir`. If I did, the session would name itself host with `term + 1` and, on returning, would overwrite the real room. I am considered offline when no broker is ready, when I do not hear my own heartbeat within 10 s, or when a tick arrives more than 3 ticks late (frozen tab, sleeping machine). On returning, `reanudar()` resets the silence counters, re-announces the peer and calls `alEntrar` again for each known peer, so that the host resends the state that was missed.

**Limited presence.** `pres` is merged (only the latest counts), goes with QoS 0, at a maximum of 8 per second (every 125 ms) and **through a single broker**: the first one connected according to the order of `RED.BROKERS`. With a single live broker, at half the rate.

**Connection status.** `enLinea()` returns `{ listos, total }`: how many brokers are in use. `listos` is 0 if none is ready or if the echo of one's own heartbeats does not come back (a socket can stay "connected" for a while with the network already down). With `listos: 0` the lobby shows "SIN CONEXIÓN · REINTENTANDO…". mqtt.js reconnects by itself every 2 s and the transport resubscribes on every `connect`.

**Changing transport** only requires writing another one with the same interface. The session and the protocol do not change.

## 10. Tests

`pruebas/index.html` runs three suites one after another, 55 tests in total.

**Rules** (`pruebas-reglas.js`, 21 tests, names prefixed `Reglas ·`; `?solo=reglas`) over a fixture of its own with invented (not real) data, injected with `usarDatos`: DEC-10, limit = minimum between contribution and cap, the six bars, design events by difficulty, review routes, MEC-12, sign-offs, vacant roles, action validation, briefing, determinism of `simular`, G-12 with a seed sweep, the three scoring rules, redesign from the debrief, empty or broken state and workshop merge.

**Protocol and session** (`pruebas.js`, 16 tests) over the simulated network `transporte-memoria.js`, with delays, asymmetric discovery and departures: simultaneous startup, role conflict, a host that leaves with an intent in flight, reload of a player and of the host, fifth player, different version, starting a mission without all roles, workshops per role, merge of two hosts, a newcomer that does not reset a game, a host that returns before its departure is noticed, return after a long outage (player and host), malformed intents and intents repeated over a slow network.

**MQTT transport** (`pruebas-transporte.js`, 18 tests, names prefixed `MQTT ·`) over `broker-falso.js`: in-memory brokers that implement the subset of mqtt.js used by the transport (SUBACK, delivery to the sender itself, Last Will, clean `end(false)`, reconnection) and allow delaying, losing messages, cutting a client, taking down a broker or leaving a zombie socket (still `connected` but nothing comes in or out). They cover:

- three brokers and four peers: discovery, single delivery of each reliable message, directed messages and absence of echo;
- a broker down from the start and another one that loses 40 %;
- Last Will from a single broker (no `alSalir`) and total cut without farewell (with `alSalir`), versus `salir()` (instant);
- late duplicate after a farewell;
- merged, limited, single-broker presence;
- `enLinea()`;
- one's own outage (cut sockets, zombie and zombie with reconnection), on the transport alone and with the session on top: nobody marks anyone as gone, no host is named, `term` does not go up, on returning it reconverges with its role and `version` never fires;
- host outage: handover and, on returning, it yields and keeps its role;
- four full sessions (one host, four connected, role and mission replicated), also with a broker down and another with losses;
- resynchronization: an `estado` lost on all brokers is recovered by itself.

Page parameters: `?solo=text` runs only the tests whose name contains it (`?solo=mqtt` for the new suite), `?veces=N` repeats them N times to catch intermittent failures and `?lento=K` multiplies the times of the MQTT suite by K (if a test fails with 1 and passes with 3, it was an artifact of the speed-up). A "el hilo se atascó" (the thread got stuck) warning next to a test means the browser throttled the clock and the result is not reliable.

## 11. Known limits

- **Public brokers with no service guarantee.** `broker.hivemq.com`, `test.mosquitto.org` and `broker.emqx.io` are for testing: they can go down, throttle or change without notice. Having three reduces the risk, it does not remove it.
- **Ports other than 443.** They use 8884, 8081 and 8084. A network that only lets 443 out (or filters ports) may block all of them. Then the lobby shows "SIN CONEXIÓN · REINTENTANDO…" and no game is possible from that network.
- **Rooms without a secret.** The topics are public: anyone who knows the room code can read and write in it, and impersonate a player.
- **Rate limit.** EMQX drops messages above ~10 per second per client. That is why presence is limited to 8 per second and goes through a single broker.
- **No order between brokers.** The same message can arrive earlier through one broker than another, and different messages can cross. The design tolerates it (full state with tag, deduplication), but order cannot be relied on.
- **Slow failure detection.** A peer that leaves without saying goodbye takes between ≈8 s (Last Will) and ≈16 s (heartbeats only) to be considered gone.
- **Guaranteed reliability.** It would require a relay of our own on port 443 (for example Cloudflare Workers with Durable Objects, Firebase or Supabase, which require an account). It would be enough to write another transport with the same interface.
- Authority is trust-based: a player who modifies their browser and becomes host can cheat. In a cooperative game this is not a problem.
